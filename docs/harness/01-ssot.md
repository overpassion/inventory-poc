### 0.5 충돌 시 판단 권한 ★

**에이전트의 임의 충돌 해소 = 판단 기준 1개 삭제.**

문서끼리 어긋날 때 에이전트가 한쪽을 골라버리면, 그 순간 조직이 유지하던 판단 기준 하나가 조용히 사라진다. 아래 4가지 외의 충돌은 **사람에게 넘긴다.**

| 충돌 | 처리 |
|---|---|
| **작업 지시(Issue)** ↔ 요구사항 · 아키텍처 · 하네스 규칙 | **중단한다.** 지시를 실행하지 않고 사람에게 알린다 |
| **참고문서** ↔ **SSOT** | **SSOT를 따른다** |
| **계획 문서** ↔ **요구사항** | **요구사항을 따른다** |
| **SSOT** ↔ **SSOT** | **구현하지 않는다.** 사람이 기준을 고칠 때까지 멈춘다 |

#### 문서 등급

| 등급 | 해당 문서 |
|---|---|
| **SSOT (규범)** | 이 문서. 그리고 추출 원본인 `01-requirements.md` · `06-architecture.md` |
| **계획 문서** | `07-plan.md` |
| **참고문서** | `02-personas` · `03-scenarios` · `04-engagement` · `HANDOVER` · `mockups/` · `docs/screenshots/` |
| **미분류** | `05-design.md` — SSOT인지 참고문서인지 미정 → `ESCALATE-05` |

#### 코드는 판단 기준이 아니다 — 단, 규범 진술에 한해서

**규범 진술**(무엇을 해야 하는가)이 코드와 어긋나면, **코드가 그렇다는 사실은 충돌을 해소하지 않는다.** 스펙이 FEFO인데 코드가 LEFO라면 LEFO가 정답이 되는 게 아니다. 어느 쪽을 고칠지는 **사람의 판단**이며, 에이전트는 §6.1에 올리고 멈춘다.

**서술 진술**(무엇이 있는가)은 다르다. 파일 이름·경로·버전처럼 **확인하면 끝나는 사실**에는 삭제될 판단 기준이 없다. 문서가 낡았을 뿐이다.

| 종류 | 예 | 처리 |
|---|---|---|
| **규범** | 배분 전략, 사유 체계, 소유권·문서 등급, SSOT 내부 모순 | **차단** → §6.1 `ESCALATE-*` |
| **서술** | 파일명·경로·존재 여부·버전·스크립트 내용 | **에이전트가 갱신** → §6.2 `DRIFT-*` |
| **구현 갭** | SSOT가 요구하는데 코드에 아직 없음 | **할 일** → §6.3 `GAP-*` |

**`DRIFT` 규칙**
- 에이전트가 **실물을 직접 확인**한 뒤 문서를 현실에 맞춘다
- **무엇을 왜 고쳤는지 반드시 보고**한다 (조용히 고치지 않는다)
- 그 서술이 규범적 의미를 띠면 — 예를 들어 폴더 구조가 `RULE-01`("재고 변경은 `lib/stock.ts` 한 곳")의 근거가 되는 경우 — **`ESCALATE`로 올린다**
- 판정이 애매하면 `ESCALATE`로 보낸다. 서술로 잘못 분류해 규범을 지우는 쪽이 더 나쁘다

### 0.6 보호 영역과 소유권 ★

**영역별로 읽기 권한과 변경 권한을 분리한다.**

| 영역 | AI | 사람 |
|---|---|---|
| 애플리케이션 코드 | **Issue 범위 안에서 수정** | 최종 승인 |
| Issue별 테스트 | **작성 · 수정** | 전제 검토 |
| 요구사항 · 아키텍처 | **읽기** | 변경 · 승인 |
| 하네스 핵심 규칙 | **읽기** | 변경 · 승인 |
| 검증 스크립트 | **실행** | 정책 변경 승인 |

#### 권한 등급의 뜻

| 등급 | 뜻 |
|---|---|
| **읽기** | 내용을 근거로 쓸 수 있으나 **파일을 고치지 않는다.** 고칠 필요를 발견하면 `ESCALATE-*` 에 올리고 멈춘다 |
| **Issue 범위 안에서 수정** | 지시가 명시한 범위만 손댄다. 범위 밖의 개선거리는 **발견해도 고치지 않고 보고한다** |
| **작성 · 수정** | 자유롭게 만든다. 다만 **테스트가 무엇을 전제하는지는 사람이 검토한다** — 전제가 틀리면 초록 불이 거짓말이 된다 |
| **실행** | 돌려서 결과를 쓴다. **스크립트 자체와 통과 기준은 고치지 않는다** |

#### 이 저장소에서의 경로 매핑

| 영역 | 경로 | AI 권한 |
|---|---|---|
| 애플리케이션 코드 | `src/**` · `prisma/seed.ts` · `prisma/migrations/**` | Issue 범위 내 수정 |
| Issue별 테스트 | `tests/**` | 작성 · 수정 |
| 요구사항 · 아키텍처 | `docs/01-requirements.md` · `docs/06-architecture.md` · **이 문서 §1~§5** | 읽기 |
| 하네스 핵심 규칙 | `AGENTS.md`(진입점) · `CLAUDE.md` · **이 문서 §0 · §6.1 · §8** · `02-verification.md` · `03-loop.md` · `04-workflow.md` | 읽기 |
| 검증 스크립트 | `scripts/verify-*.ts` · `scripts/snapshot.ts` · `package.json` 의 `scripts` | 실행 |
| **등급 미정** | `prisma/schema.prisma` · `docs/02`~`05` · `docs/07` · `README.md` · 설정 파일(`*.config.*` `.env*` `.gitignore`) | → `ESCALATE-06` |

> `prisma/schema.prisma` 가 *애플리케이션 코드*인지 *아키텍처*인지는 특히 중요하다. 아키텍처라면 AI는 스키마를 고칠 수 없고, 데이터 모델 변경은 전부 사람 승인을 거친다.

#### 이 문서 자체에 적용

이 문서는 **요구사항·아키텍처(§1~§5)** 와 **하네스 핵심 규칙(§0·§6.1·§8)** 을 함께 담으므로, AI에게는 **전체가 읽기 전용**이다. 실제로 §0.5와 §0.6은 사람이 지시해 추가됐다 (2026-09-15).

**AI가 갱신할 수 있는 칸** — 판단이 아니라 관측을 적는 곳에 한한다:

| 칸 | 조건 |
|---|---|
| §0.4 구현상태 | 검증 루프의 결과로만. 갱신 사실을 보고한다 |
| §6.2 `DRIFT-*` | 서술 드리프트를 발견하면 추가하고, 실물 확인 후 해당 서술을 갱신한다. **고친 내용을 보고한다** |
| §6.3 `GAP-*` | 새 갭을 발견하면 추가. 기존 항목의 해석은 바꾸지 않는다 |

이 두 칸 외에는 **사람의 지시 없이 이 문서를 고치지 않는다.**

#### 강제 수단

```
npm run verify:harness              # 보호 경로가 바뀌었으면 exit 1
npm run verify:harness -- --update  # 기준선 갱신 — 사람이 승인한 뒤에만
```

`scripts/verify-harness.ts` 가 위 경로 매핑에서 **AI가 고칠 수 없는 파일 11개**의 sha256을 `docs/harness/protected.json` 의 기준선과 대조한다. 줄바꿈은 정규화 후 해시하므로 CRLF/LF 차이로는 실패하지 않는다.

**이것은 사후 탐지이지 사전 차단이 아니다.** 편집 자체를 막으려면 훅이 필요하다. → `OPEN-04`

## 1. 도메인 (DOM)

### DOM-01. 프로젝트 정의

여러 재고 거점(풀필먼트 3사 + 자사 창고 1곳)에 흩어진 재고를 **유통기한 기준 선입선출(FEFO)** 로 관리하고, **오프라인 팝업 반출·반입**까지 추적하는 사내 재고관리 앱.

푸는 문제 3가지:
1. 재고가 4곳에 흩어져 전체 수량을 한눈에 볼 수 없다
2. 유통기한이 다른 재고가 섞여 오래된 것부터 나가는지 보장이 안 된다
3. 팝업 반출은 판매가 아니라 **위치 이동 + 부분 판매**인데 일반 재고 흐름으로 표현이 안 된다

전제: 사용자 2~3명 · 모바일 우선(데스크톱 병행) · 로그인 필수 · 모든 변경에 작성자 기록.

### DOM-02. 로트 (Lot) — 재고의 최소 단위

```
Lot = 상품(SKU) × 거점(Location) × 유통기한(expiryDate)
```

세 값이 같으면 하나의 로트로 **합쳐진다**. DB에서 `UNIQUE(productId, locationId, expiryDate)` 로 강제한다.

- 입고 배치(로트번호) 단위로는 **쪼개지 않는다.** 같은 유통기한이면 같은 물건으로 본다.
- 근거: FEFO는 유통기한 순서만 지키면 충족되고, 입고 건별로 쪼개면 현장에서 세기 어려워진다.
- **대가**: "몇 월 며칠 입고분만 리콜" 같은 추적은 불가능하다 → `OOS-04`

### DOM-03. 거점 (Location) 5종

| type | 예시 | 성격 |
|---|---|---|
| `OWN` | 자사창고 | 우리가 직접 세는 곳. **모든 이동의 출발점** |
| `FULFILLMENT` | 풀필먼트 A / B / C | 남이 세는 곳. **저쪽 수치가 진실** |
| `POPUP` | 성수 팝업 10월 | 행사 기간에만 존재. 종료 시 잔여 재고 0 |
| `TRANSIT` | (가상) 배송 중 | 자사창고를 떠났으나 풀필먼트에 아직 안 잡힌 재고 |
| `DISPOSAL` | (가상) 폐기 | 기한 만료로 사람이 확정해 뺀 재고 |

**가상 거점을 두는 이유**: 재고가 "사라지는" 상태를 만들지 않기 위해서다. 모든 수량 변화는 어딘가 → 어딘가의 이동으로 기록되며, 그래야 총량 검증이 가능하다. → `INV-04`

### DOM-04. 엔터티 9개

`User` · `Product` · `Location` · `Lot` · `Movement` · `Transfer` · `TransferLine` · `Popup` · `PopupPlan`

> ⚠️ **잠정값 — 사람 판단 대기.** `01 §4`의 개념 모델은 7개이고 `prisma/schema.prisma` 에는 9개가 있다 (`TransferLine` `PopupPlan` 추가). 어느 쪽에 맞출지는 정해지지 않았다. → §6.1 `ESCALATE-02`

**진실의 원천**: `Movement` 가 이력의 원본이고, `Lot.quantity` 는 그 결과를 빠르게 읽기 위한 **현재값(파생)** 이다. 둘은 항상 같은 트랜잭션에서 갱신한다. → `RULE-02`

### DOM-05. Movement 타입 7종

`INBOUND` · `OUTBOUND` · `TRANSFER` · `POPUP_OUT` · `POPUP_IN` · `ADJUST` · `DISPOSE`

`from_location_id` / `to_location_id` 가 `null` 이면 그쪽이 **외부**다 (입고의 출발지, 출고의 도착지).

### DOM-06. 사유 코드 10종

재고가 줄거나 느는 모든 기록에 사유가 붙는다. **사유별 집계가 있어야 실사에서 차이가 났을 때 원인을 짚을 수 있다.**

**감소 (외부로 나감)**

| 코드 | 이름 | 쓰이는 곳 |
|---|---|---|
| `SALE` | 판매 — **기본값** | 출고 · 풀필먼트 일일반영 · 팝업정산 |
| `SAMPLE` | 시식·증정 (대가 없이 나간 것) | 출고 · 팝업정산 |
| `DAMAGE` | 파손 | 출고 · 조정 |
| `LOSS` | 분실 (대개 실사에서 발견) | 출고 · 조정 |
| `DISPOSE` | 폐기 (유통기한 만료, `REQ-F-09`에서만) | 폐기 처리 |
| `OTHER` | 기타 — **메모 필수** | 전체 |

**증가 (외부에서 들어옴)**

| 코드 | 이름 | 비고 |
|---|---|---|
| `PURCHASE` | 입고 — **기본값** | 매입·생산 |
| `RETURN` | 반품 재입고 | 어느 박스가 왔는지 모르므로 **유통기한을 다시 입력**한다 |
| `OTHER` | 기타 — **메모 필수** | |

**조정 전용 (양방향)**

| 코드 | 이름 | 비고 |
|---|---|---|
| `COUNT_DIFF` | 대조 차이 | 원인 불명이지만 숫자를 맞춰야 할 때 |
| `INPUT_ERROR` | 오입력 정정 | |

> 조정에서 원인이 분명하면 `DAMAGE`·`LOSS`, 모르면 `COUNT_DIFF`.
> 자사창고에 `COUNT_DIFF`가 자주 쌓이면 창고 관리에 구멍이 있다는 신호다.

판매처(거래처명·판매 채널) 구분은 하지 않는다 → `OOS-06`

### DOM-07. 사유가 붙지 않는 이동 4종

장소만 바뀌는 것이므로 사유 체계를 쓰지 않는다. **총 재고는 변하지 않는다.**

| 이동 | 경로 |
|---|---|
| 풀필먼트 발송 | 자사창고 → 배송 중 |
| 도착 확인 | 배송 중 → 풀필먼트 |
| 팝업 반출 (추가 반출 포함) | 자사창고 → 팝업 |
| 팝업 복귀 | 팝업 → 자사창고 |

> **팝업에서 돌아온 물건은 반품이 아니다.** 반품(`RETURN`)은 외부에 나갔던 물건이 우리 재고로 새로 들어오는 것이고, 팝업 복귀는 우리 재고가 자기 자리로 돌아오는 것이다. 유통기한도 반출 기록에 남아 있어 다시 물을 필요가 없다.
> 팝업 정산에서 사유가 붙는 대상은 **돌아오지 않은 수량뿐**이다 (`SALE` 또는 `SAMPLE`).

#### `REQ-F-01` 상품(SKU) 관리 ⬜
- SKU 코드 · 상품명 · 단위 · **유통기한 경고 임계일(품목마다 다름)**
- 임계일 기본값 제공(예: 60일), 개별 수정 가능

**수용 기준** — 설정 화면에서 상품을 추가하면 목록에 즉시 반영되고, 임계일을 바꾸면 해당 상품의 임박 판정이 달라진다.
**상태 근거** — `/settings` 라우트 없음. 현재 상품은 시드로만 생성된다.

#### `REQ-F-02` 거점 관리 ⬜
- 거점 추가/수정 (유형: 자사창고 / 풀필먼트 / 팝업 / 시스템)
- 팝업 거점은 **행사 단위로 생성되고 종료 후 비활성화**

**수용 기준** — 풀필먼트사 실제 이름이 정해지면 화면에서 거점을 추가할 수 있다 (`ASM-06`).
**상태 근거** — `/settings` 라우트 없음.

#### `REQ-F-03` 재고 현황 조회 ✅
- **SKU별 전체 수량** + 거점별 분해 (접었다 펼치기)
- 유통기한 임박 재고 강조 (임계일 이내 / 이미 만료)
- 검색·필터: SKU명 · 거점 · 임박 여부

**수용 기준** — 검색 후 "지금 출고 가능 N개"를 즉답하고, 펼치면 거점별로 분해된다. → `DOD-01`

#### `REQ-F-04` 입고 ✅
- 자사창고 입고: 상품 + 유통기한 + 수량 → **로트 생성 또는 기존 로트에 합산**
- 풀필먼트 직입고도 동일하게 기록 가능

**수용 기준** — 유통기한이 다른 같은 상품을 2건 입고하면 **로트 2개로 분리**된다. → `DOD-02`

#### `REQ-F-05` 출고 (판매·발송) ✅
- **출고 사유를 반드시 남긴다** (기본값 `SALE` — `DOM-06`)
- **FEFO 강제**: 유통기한이 가장 임박한 로트를 자동 선택. 외부로 나가는 **모든 감소**에 적용
- 다른 로트를 선택하려면 **사유 입력 필수** (예: "고객 요청", "임박분 물류 미도착")
- 수량이 여러 로트에 걸치면 **임박 순으로 자동 배분하여 제안**

**수용 기준** — 출고 시 임박 로트가 자동 선택되고, 다른 로트를 고르면 사유를 요구한다. → `DOD-03` · `RULE-04` · `INV-01,02`

#### `REQ-F-06` 거점 간 이동 (자사창고 → 풀필먼트) ✅
- **2단계 처리**: 발송(출발) → 입고 확인(도착)
- 발송 시 재고는 `TRANSIT`(배송 중)으로 이동 — 자사창고에서는 빠지지만 **총량은 유지**
- 도착 확인 시 목적지 거점 로트로 편입
- 미확인 이동 목록을 별도 표시 (오래 방치된 건 경고)
- **배분은 LEFO** — 상세는 `RULE-04`

**수용 기준** — 발송하면 `배송 중`에 잡히고, 도착 확인 전까지 총 재고 수량은 변하지 않는다. → `DOD-04` · `INV-04`

#### `REQ-F-07` 팝업 반출·반입 ✅
1. **팝업 생성** — 이름 · 기간 · 출발 거점(자사창고)
2. **반출** — 상품·로트 선택 → 팝업 거점으로 이동. FEFO 적용
3. **행사 중** — 팝업 거점에 재고가 그대로 잡혀 있음 (판매 건별 기록 안 함 → `OOS-05`)
4. **반입 정산** — 복귀 시 **남은 실물 수량만 입력** → `반출 − 반입 = 차감` 으로 역산
   - 차감분을 **판매 / 시식·증정**으로 나눠 입력 (기본 0)
   - **시식 수량이 차감분보다 클 수 없다** → `RULE-07` · `INV-06`
   - 역산 결과를 화면에서 확인 후 확정
   - 확정 시: 잔여분은 자사창고 복귀, 판매분은 출고 처리
   - **로트별로 반입 수량을 입력**해야 유통기한 정보가 보존된다
5. **정산 결과 요약** — 반출 / 판매 / 반입 / 소진율

**수용 기준** — 30개 반출 → 18개 반입 정산 시 차감 12개가 역산되고, 시식 2개 입력 시 판매 10 / 시식 2로 기록되며 자사창고 재고가 18개 복귀한다. → `DOD-06` · `INV-05`

#### `REQ-F-08` 재고 조정 (실사) ⬜ — **필수**
- "풀필먼트사 수치가 진실"이라는 원칙의 **실행 수단**
- 거점·로트별 **실물 수량 입력** → 장부와의 차이 표시 → 확정 시 조정 기록 생성
- 조정에는 **사유 입력 필수** — `COUNT_DIFF` / `DAMAGE` / `LOSS` / `INPUT_ERROR` / `OTHER`
- 조정 이력은 **삭제 불가**

**수용 기준** — 실사 조정 시 차이가 표시되고, **사유 없이는 확정되지 않는다.** → `DOD-08`
**상태 근거** — `src/actions/adjust.ts` 없음.
**주의** — 자사창고는 *로트별 실물 카운트*, 풀필먼트는 *수치 반영*으로 성격이 다르다.

#### `REQ-F-09` 유통기한 만료 처리 + 알림 🟡
- **자동 폐기는 하지 않는다.** 기한이 지나도 사람이 확정하기 전까지 재고에 남아 있다
- **앱 안에서 알림을 준다**
  - 상단 알림 배지: 임박 N건 / 만료 N건 / 폐기 대기 N건
  - 홈 상단 알림 카드 → 해당 로트 목록으로 이동
  - 목록에서 임박·만료 로트는 **아이콘 + 텍스트**로 구분 (`REQ-N-06`)
- 폐기 확정 시 `DISPOSAL` 거점으로 이동 + 사유 기록. 되돌리려면 상쇄 기록
- 알림 채널은 **앱 내 표시만** → `OOS-08`

**수용 기준** — 임계일 이내 로트가 알림에 뜨고, 폐기 확정 전까지 재고에서 빠지지 않는다. → `DOD-09`
**상태 근거** — 홈 할 일 배너는 있으나 `/expiry` 라우트가 없어 **링크가 404**.

#### `REQ-F-10` 이력 / 감사 로그 🟡
- 모든 수량 변화는 `Movement` 로 남는다: 언제 · 누가 · 어떤 로트 · 출발 → 도착 · 수량 · 사유
- 기록은 **수정·삭제 불가.** 잘못 입력했으면 반대 기록으로 상쇄 → `RULE-08`
- SKU별 / 거점별 이력 조회

**수용 기준** — 이력 화면에서 모든 행위의 **누가·언제**가 확인된다. → `DOD-11`
**상태 근거** — `Movement` 기록은 동작하나 `/history` 라우트 없음 (조회·취소 UI 미구현).

#### `REQ-F-11` 로그인 ✅
- 이메일 + 비밀번호. 계정은 **관리자가 등록** (공개 가입 없음 → `ASM-04`)
- 모든 기록에 작성자가 남는다

**수용 기준** — 2명이 각자 폰과 PC에서 접속해 같은 재고를 본다. → `DOD-01`

### 3.3 계층 구조

```
Next.js (React UI + Server Components)
        ↓
Server Actions            ← 유효성 검증 · 세션에서 userId
        ↓
db.$transaction()
        ↓
Domain Logic              ← FEFO 조회·정산 계산도 같은 tx 사용
  ├─ allocateLots(tx)
  ├─ applyMovement(tx)
  ├─ settlePopup(tx)
  └─ reverseMovement(tx)
        ↓
Prisma ORM  →  SQLite
        ↓
revalidatePath('/')       ← 서버 컴포넌트 재렌더 (전역 상태 없음)
```

- React 컴포넌트가 Prisma를 직접 호출하지 않는다. **서버 영역에서만 Prisma를 사용한다.**
- 복잡한 조회가 필요해지면 Prisma를 유지하면서 **제한적으로 raw SQL** 을 쓸 수 있다.

### 3.5 핵심 로직 계약

#### `applyMovement(tx, input)` — `lib/stock.ts`

**재고 증감의 유일한 통로.** → `RULE-01`

```ts
type MovementInput = {
  type: MovementType
  reason?: ReasonCode          // 위치 이동(TRANSFER/POPUP_*)에는 없음 (DOM-07)
  productId: number
  expiryDate: Date
  quantity: number             // 양수만
  fromLocationId?: number      // 없으면 외부에서 들어옴
  toLocationId?: number        // 없으면 외부로 나감
  userId: number
  transferId?: number
  popupId?: number
  note?: string
}
```

1. `quantity <= 0` 이면 예외
2. 출발지 차감 — 로트가 없거나 `lot.quantity < quantity` 면 `InsufficientStockError` (음수 재고 금지)
3. 도착지 가산 — 없으면 로트 생성 (`upsert`)
4. `Movement` 기록 — **항상 함께, 항상 같은 트랜잭션**

#### `planAllocation(lots, quantity, strategy)` — `lib/fefo.ts`

**순수 함수.** 화면 미리보기와 서버가 같은 결과를 내야 한다.

```ts
export const ALLOCATION = { FEFO: 'FEFO', LEFO: 'LEFO' } as const
// 정렬: LEFO 면 유통기한 내림차순, 아니면 오름차순. 동률이면 lot.id
// 반환: { plan: Allocation[], shortage: number }
```

`allocateLots(tx, ...)` 는 **서버 전용** — 저장 직전 DB의 현재 재고로 다시 계산한다.

#### `settlePopup(popupId, input)` — `actions/popup.ts`

```
누적 반출 = POPUP_OUT 합계 − POPUP_IN 합계(이전 정산분)
차감      = 누적 반출 − 이번 반입
판매      = 차감 − 시식·증정
```

정산 확정 시 로트별로:
① 판매분 `POPUP_OUT`/`SALE` (팝업 → 외부) ② 시식분 `POPUP_OUT`/`SAMPLE` ③ 잔여 복귀 `POPUP_IN` (팝업 → 자사창고, **사유 없음**)
→ `Popup.status = 'CLOSED'`

#### `reverseMovement(movementId)` — `lib/stock.ts`

삭제하지 않는다. 방향을 뒤집은 `Movement` 를 만들고 `reversalOfId` 로 원본을 가리킨다.

### 3.6 인증

```
로그인 폼 → actions/auth.ts
   bcrypt.compare(입력, user.passwordHash)
   → jose로 JWT 서명 → httpOnly · sameSite=lax 쿠키 (7일)

```

- 회원가입 화면 없음. 계정은 시드로 심고 설정 화면에서 추가 (`REQ-F-11`, `ASM-04`)
- 비밀번호는 **bcrypt 해시로만** 저장. 시드 계정도 마찬가지
- 역할 구분은 `role` 필드만 두고 **MVP에서는 기능 차이를 두지 않는다** → `OOS-07`
- 세션은 **DB까지 검증한다** (`lib/auth.ts` 의 `requireUser`). `lib/session.ts` 는 쿠키만 보므로 proxy 전용

### 3.7 동시성 · 성능

- SQLite는 **WAL 모드**로 연다 (`PRAGMA journal_mode = WAL`) — 읽기와 쓰기가 서로 막지 않는다
- 2~3명 규모에서 쓰기 충돌은 사실상 없다. 모든 재고 변경은 트랜잭션이므로 **충돌 시 재시도 1회**
- `Lot` 에 `@@index([locationId, expiryDate])` — FEFO 조회가 정렬 없이 인덱스로 끝난다
- 목록 조회는 서버 컴포넌트에서 한 번에 집계 → `REQ-N-04`

### 4.2 코드 강제 규칙 (RULE)

| ID | 규칙 |
|---|---|
| `RULE-01` | **재고 수량을 바꾸는 코드는 `lib/stock.ts` 의 `applyMovement()` 한 곳에만 존재한다.** 화면·액션은 절대 `prisma.lot.update()` 를 직접 호출하지 않는다 |
| `RULE-02` | `applyMovement()` 는 반드시 `prisma.$transaction()` 안에서 호출한다. **`Lot` 갱신과 `Movement` 기록은 원자적으로 성공하거나 함께 롤백된다** |
| `RULE-03` | **음수 재고 금지.** 출발지 잔량이 모자라면 `InsufficientStockError` 를 던지고 아무것도 바꾸지 않는다 (화면에서는 저장 버튼 비활성) |
| `RULE-04` | **배분 방향은 하나가 아니다** — 아래 표 |
| `RULE-05` | 배분은 **반드시 한 거점 안에서만** 한다. 자사창고에서 빼는데 풀필먼트 재고를 제안하면 안 된다 |
| `RULE-06` | **만료된 로트도 배분 후보에 포함한다** (실물이 아직 있으므로). 화면에서 빨간 배지로 경고한다 |
| `RULE-07` | **팝업 정산은 누적 반출 기준.** 1차 반출만 놓고 계산하면 판매량이 틀린다. `시식 ≤ 차감` 을 위반하면 저장 거부 |
| `RULE-08` | **취소는 상쇄 기록.** 삭제하지 않는다. **하나의 원본 `Movement` 에는 상쇄를 한 번만 허용** — `reverseMovement()` 가 같은 `reversalOfId` 기록의 존재를 트랜잭션 안에서 확인하고, 있으면 거부한다 |
| `RULE-09` | 여러 로트에 걸친 출고는 `applyMovement()` 를 **로트 수만큼** 호출한다 (한 트랜잭션 안에서) |
| `RULE-10` | 사유 `OTHER` 는 **메모 없이 저장할 수 없다.** 사유는 화면에서 기본값이 미리 선택되어 있고, 바꿀 때만 손이 간다 |

#### `RULE-04` 배분 방향

| 동작 | 전략 | 이유 |
|---|---|---|
| 출고 (판매·시식·파손) | **FEFO** 임박분 먼저 | 곧 소비되므로 임박분부터 내보내야 안 버린다 |
| 풀필먼트 일일 반영 | **FEFO** 임박분 먼저 | 이미 고객에게 나간 물량의 차감 |
| 팝업 반출 | **FEFO** 임박분 먼저 | 현장에서 며칠 안에 팔린다 *(실무 확인 2026-08-18)* |
| **풀필먼트 발송** | **LEFO 넉넉한 분 먼저** | **도착 3~5일 + 판매 대기.** 임박분을 보내면 팔리기 전에 만료된다 |
| 폐기 | 만료분 지정 | — |

- 수동 선택 시 `reason` 필수 (`REQ-F-05`)
- LEFO에서 넉넉한 재고가 모자라면 임박분이 섞인다. 이때 화면에 **⚠ 임박분이 포함됐습니다** 를 띄운다

> 이 표는 원래 `01 §3 F6` 과 `06 §4.2` 에 **중복**되어 있었고 **양쪽 내용이 일치**한다. 충돌이 아니므로 단일화했다 — 삭제된 판단 기준은 없다. → §6.4 `RESOLVED-01`

## 6. 충돌 기록

§0.5의 판단 권한 규칙에 따라 분류한다.

### 6.1 사람 판단 대기 (ESCALATE) — **구현 차단**

**에이전트가 고르면 안 되는 충돌.** 사람이 기준을 고칠 때까지 해당 항목에 의존하는 구현을 하지 않는다.

| ID | 충돌 | 유형 | 확인된 사실 | 사람이 정할 것 |
|---|---|---|---|---|
| `ESCALATE-02` | `01 §4` 개념 모델 **7개** vs `schema.prisma` **9개** (`TransferLine` `PopupPlan` 추가) | SSOT ↔ 코드 | 코드에 9개 존재 | 개념 모델에 2개를 추가할 것인가, 아니면 *"개념 모델은 의도적으로 추상"* 으로 둘 것인가 |
| `ESCALATE-05` | `06 §2` 의 `FefoPreview.tsx` vs `05-design.md` 의 `<AllocationPreview>` | **등급 미정** | 이름 불일치 | 먼저 `05-design.md` 가 SSOT인지 참고문서인지 정해야 판단 규칙이 결정된다 (§0.5) |
| `ESCALATE-06` | §0.6 경로 매핑에서 **보호 영역이 정해지지 않은 파일들** | **소유권 미정** | `prisma/schema.prisma` · `docs/02`~`05` · `docs/07` · `README.md` · 설정 파일 | 각각 어느 영역에 속하는가. 특히 **`schema.prisma` 가 애플리케이션 코드인지 아키텍처인지** — 후자면 AI는 스키마를 고칠 수 없다 |

> `ESCALATE-07`(규칙 본문 이중화)은 **사람이 ② 안을 선택해 해소**했다 → §6.4 `RESOLVED-04`
> `ESCALATE-01` `03` `04` `08` 은 **서술 드리프트로 재분류**됐다 (2026-09-15, 사람 판단) → §6.2 `DRIFT-*`

> **`DOM-04` 는 `ESCALATE-02` 에 걸려 있어 잠정값이다.**
> 이 문서는 조사 결과(코드의 실제 상태)를 적어 두었을 뿐, **어느 쪽이 옳은지 판정하지 않았다.**

### 6.2 서술 드리프트 (DRIFT) — 에이전트가 갱신

SSOT의 **서술 진술**이 확인 가능한 현실과 어긋난 것 (§0.5). 판단이 갈리지 않으므로 **에이전트가 실물을 확인해 문서를 고치고 보고**한다.

| ID | 드리프트 | 확인된 사실 | 상태 |
|---|---|---|---|
| `DRIFT-01` | `06 §3` 코드블록은 `provider = "prisma-client-js"`, `06 §1` 표는 `prisma-client` | `prisma/schema.prisma` 는 **`prisma-client`** — §1이 맞고 §3 코드블록이 오기 | 미적용 |
| `DRIFT-02` | `06 §2` 는 `src/middleware.ts` | 실제 **`src/proxy.ts`** | 미적용 |
| `DRIFT-03` | `06 §2` 는 `lib/format.ts`, 그리고 `constants.ts` `inventory.ts` `popup.ts` `auth.ts` 가 문서에 없다 | 실제 **`lib/date.ts`** + 미기재 4개 존재 | 미적용 |
| `DRIFT-04` | `06 §7` 의 `package.json` scripts 블록 | 실제는 `"dev": "npm run db:ensure && next dev"`, `seed:reset` 도 다름 | 미적용 |

> **왜 차단이 아닌가** — 파일 이름이 `proxy.ts`인 것은 *확인하면 끝나는 사실*이지 사람이 정할 일이 아니다. 네 건 모두 `ESCALATE` 에 있던 동안 **아무 결정도 만들지 못한 채 주차만 돼 있었다.**
>
> **왜 그래도 기록하는가** — 조용히 고치면 "문서가 왜 바뀌었는지"가 사라진다. 갱신할 때 이 표에 근거를 남긴다.

**적용 전 확인** — `06 §2` 폴더 구조는 `RULE-01`(재고 변경은 `lib/stock.ts` 한 곳)의 근거이기도 하다. `stock.ts` 의 위치·역할을 바꾸는 변경이라면 `DRIFT` 가 아니라 `ESCALATE` 다. `DRIFT-02`·`03` 은 그 파일을 건드리지 않는다.

## 8. 갱신 규칙

1. **충돌을 만나면 §0.5로 간다.** 규칙이 답을 주지 않으면 `ESCALATE-*` 에 올리고 **멈춘다.** 에이전트가 한쪽을 고르는 순간 판단 기준 하나가 사라진다.
2. **파일을 고치기 전에 §0.6에서 권한을 확인한다.** AI가 이 문서를 고칠 수 있는 칸은 §0.4 구현상태와 §6.3 `GAP-*` 둘뿐이다.
3. 이 문서를 고치면 **§6에 근거를 남긴다.**
4. **ID는 재사용하지 않는다.** 폐기된 항목은 번호를 비우고 `(폐기)` 로 남긴다.
5. `OOS-*` 를 넘어서는 구현은 **하지 않는다.** 범위를 넓히려면 먼저 이 문서에서 해당 항목을 빼야 한다.
6. 구현상태(§0.4) 갱신은 검증 루프가 생긴 뒤 그 결과로만 한다. 그 전까지는 파일 존재 여부 기준의 잠정값이다.
7. `03-scenarios.md` `05-design.md` `07-plan.md` 를 추출 범위에 넣을 때는 §0.2 · `ESCALATE-05` · `OPEN-03` 을 먼저 정리한다.
8. **보호 경로를 사람이 승인해 고쳤으면 `npm run verify:harness -- --update` 로 기준선을 갱신한다.** 갱신하지 않으면 이후 검증이 계속 실패한다.
