## 2. 브랜치

`WF-02` 는 실제 사고에서 나왔다 — 2026-09-16, 에이전트가 브랜치를 확인하지 않고 이슈 구현을 `main` 에 바로 커밋했다. 푸시 전에 발견해 옮겼지만, **기계가 막아주지 않는다.**

```bash
git switch -c <타입>/<슬러그> main    # 항상 main 에서 딴다
```

| 타입 | 쓰는 곳 | 예 |
|---|---|---|
| `feat/` | 이슈 구현 | `feat/issue-1-outbound-expiry-badge` |
| `fix/` | 버그 수정 | `fix/issue-7-transfer-delay` |
| `docs/` | 문서 · 하네스 | `docs/harness-restructure` |
| `ci/` | 워크플로 · 빌드 | `ci/node-24` |

이슈가 있으면 슬러그에 **`issue-N`** 을 넣는다. 나중에 커밋·브랜치·이슈가 서로 찾아진다.

---

## 3. 커밋

**형식** — Conventional Commits. 저장소가 이미 `feat` `fix` `docs` `refactor` `ci` `chore` `style` 을 쓰고 있다.

```
<타입>: <한 줄 요약>

<무엇이 문제였고 왜 이렇게 고쳤는지>

Closes #N
```

- 이슈를 닫는 커밋에는 **`Closes #N`** 을 넣는다
- **공동작업자 트레일러를 넣지 않는다** — 사용자 설정(`attribution`)으로 꺼져 있다
- 한 커밋에 한 가지 일만. 구현과 무관한 정리는 **다른 커밋**으로
- 보호 경로 변경 + `protected.json` 갱신은 **같은 커밋**에 (`WF-04`) — 나누면 그 사이 커밋에서 `verify:harness` 가 깨진다

## 4. 보고 — 무엇을 사람에게 넘기는가

루프가 끝나면([03-loop.md](./03-loop.md) §5 인계 코멘트) 아래를 함께 넘긴다.

1. **변경한 파일과 근거** — 각 변경이 어느 `REQ-F-*` · `RULE-*` · `GAP-*` 에서 왔는지
2. **종료 조건 상태** — 이슈 §3의 각 항목을 **자동 통과 / 수동 미확인 / 실패**로 구분
3. **수동 확인 항목** — 브라우저로 봐야 하는 것은 **못 봤으면 못 봤다고 쓴다**
4. **새로 발견한 것** — `DRIFT-*` · `GAP-*` 는 기록하고 진행, `ESCALATE-*` 감이면 멈추고 올린다

> 범위 밖에서 발견한 개선거리는 **고치지 않고 보고한다** (§0.6 「Issue 범위 안에서 수정」).

## 5. 머지

에이전트는 여기까지 오지 않는다. 사람이 한다 (`WF-06`).

경로가 **둘**이다. 둘 다 선형 이력을 남기지만 **커밋이 같은 것이냐**에서 갈린다.

### 5.1 로컬 fast-forward — 기본

```bash
npm run verify                        # 머지 전 대상 브랜치에서
git switch main
git merge --ff-only <브랜치>          # 포인터만 앞으로 — 커밋을 새로 만들지 않는다
npm run verify                        # main 에서 다시
git push origin main
git branch -d <브랜치>                # 로컬 정리
git push origin --delete <브랜치>     # 원격 정리
```

브랜치가 `main` 의 **직계 자손**일 때만 된다. 아니면 먼저 `git rebase main`.

2026-09-16 부터 조건이 하나 더 붙는다 — **올리는 커밋에 `verify` 초록 체크가 있어야 한다** (§6 브랜치 보호). ff-only 는 SHA 를 보존하므로 브랜치를 푸시했을 때 받은 체크가 그대로 따라온다. 브랜치를 푸시하지 않고 로컬에서만 만든 커밋은 체크가 없어 **거부된다.**

### 5.2 PR — 리뷰 단위를 남길 때

```bash
gh pr create -R overpassion/inventory-poc --base main --head <브랜치> ...
gh pr merge <번호> -R overpassion/inventory-poc --rebase --delete-branch
git pull --ff-only origin main        # 로컬 main 을 맞춘다
git branch -D <브랜치>                # SHA 가 달라져 -d 는 거부한다 (아래 참고)
```

**`-R` 을 빠뜨리지 않는다.** 포크라서 `gh` 가 기본 저장소를 upstream(`jo-narae`)으로 잡는다.

GitHub 에는 **fast-forward 가 없다.** merge commit · squash · rebase 셋뿐이고, 그중 `--rebase` 가 `--ff-only` 에 가장 가깝다.

### 5.3 무엇이 다른가

| | 5.1 `--ff-only` | 5.2 PR `--rebase` |
|---|---|---|
| 실행 위치 | 내 컴퓨터 | GitHub 서버 |
| 커밋을 새로 만드나 | **아니오** | **예** — 같은 내용으로 다시 쓴다 |
| SHA | **그대로** | **바뀐다** |
| 커미터 | 나 | GitHub |
| 이력 | 선형 | 선형 |

실측 (PR #2, 2026-09-16):

```
브랜치  2ef27f6  tree=85b647c5  commit=comghost    15:34:50
main    e4592d1  tree=85b647c5  commit=overpassion 15:41:19
        └ 내용(tree)은 동일한데 SHA 가 다르다
```

**5.1 은 내가 `verify` 를 돌린 바로 그 커밋이 `main` 에 올라간다.** 5.2 는 SHA 가 달라지므로, 엄밀히 말하면 **CI 가 검증한 커밋과 `main` 의 커밋이 다르다.** 그래서 머지 뒤 `main` 에서 CI 가 한 번 더 돈다.

로컬 브랜치도 갈라진다 — `git branch -d` 가 "머지 안 됨"으로 거부하므로 `-D` 로 지운다.

### 5.4 어느 쪽을 쓰나

| 상황 | 경로 |
|---|---|
| 기본 | **5.1** — 검증한 커밋이 그대로 올라간다 |
| 변경 단위를 남기고 싶을 때 | 5.2 — diff 와 논의가 PR 에 남는다 |
| 서명(GPG)을 쓰게 되면 | **5.1** — 5.2 는 재작성되며 서명이 깨진다 |

## 6. 알려진 빈틈

- **`WF-02` 를 기계가 막지 않는다.** 브랜치 확인은 에이전트의 습관에 달려 있다. `main` 브랜치 보호 규칙도 없다
- ~~**CI 실패가 머지를 막지 않는다.**~~ **2026-09-16 해소** — `main` 에 브랜치 보호를 걸고 `verify` 를 필수 체크로 지정했다. 실측: 빨간 PR #3 의 상태가 `UNSTABLE`(머지 가능) → `BLOCKED`(머지 불가) 로 바뀌었다. `enforce_admins: true` 라 소유자도 우회 버튼이 없다
  - 끄는 법 — `gh api -X DELETE repos/overpassion/inventory-poc/branches/main/protection` (또는 `.../protection/enforce_admins` 만)
  - **리뷰 필수는 걸지 않았다.** GitHub 은 자기 PR 을 자기가 승인하지 못한다. 포크 단독 작업에서 걸면 혼자서는 영영 머지할 수 없다
  - `strict`(브랜치가 최신이어야 함)는 **끔.** 켜면 `main` 이 움직일 때마다 리베이스 후 CI 를 다시 기다려야 한다
- **리뷰하는 사람이 따로 없다.** 포크 단독 작업이라 PR 을 열어도 자기가 열고 자기가 머지한다 — 사람이 직접 읽는 것이 유일한 검토다
- **같은 커밋에 CI 가 두 번 돈다.** 브랜치를 푸시하면 `push` 로, PR 을 열면 `pull_request` 로 각각 실행된다 (PR #2 에서 관측). 고치려면 워크플로의 `push` 를 `branches: [main]` 으로 좁히거나 `pull_request` 를 뺀다
- `WF-04` 를 어기면 **중간 커밋에서 `verify:harness` 가 깨진다.** CI는 푸시된 시점만 보므로 이를 잡지 못한다

## 7. 예정 · 미정

- ~~`main` 브랜치 보호 규칙~~ — 2026-09-16 적용 (§6). **직접 푸시는 여전히 열려 있다** (`restrictions` 미설정) — 초록 커밋이면 `main` 에 바로 푸시된다. §5.1 이 그것을 전제로 하므로 일부러 열어 뒀다. 사람만 쓰는 저장소에서 이 문을 닫을지는 미정
- **CI 가 한 번도 안 돈 커밋은 `main` 에 못 올라간다.** 워크플로가 꺼지거나 이름(`verify`)이 바뀌면 모든 푸시가 막힌다 — 그때는 보호 규칙부터 손봐야 한다
- CI 중복 실행을 고칠지 (§6) — 트리거를 좁히면 되지만, PR 없이 브랜치만 푸시할 때 CI 가 안 돌게 될 수 있다
- 언제 5.1 대신 5.2(PR)를 쓸지 — 지금은 사람이 그때그때 고른다
- 브랜치 정리 시점 — 머지 직후인지, 일정 기간 뒤인지
- 이슈 없이 시작한 작업(`WF-01` 예외)을 어떻게 다룰지 — 지금은 사용자 지시문이 곧 이슈다
