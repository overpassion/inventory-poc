# 03. 루프 — 언제 멈추는가

## 1. 핵심 규칙

| ID | 규칙 |
|---|---|
| `LOOP-01` | **1회 = 코드를 고치고 `npm run verify` 를 돌린 것.** 읽기 · 조사 · 계획은 세지 않는다 |
| `LOOP-02` | 기본 **최대 3회**. 이슈 §6 이 다른 수를 적었으면 그쪽이 우선한다 |
| `LOOP-03` | 횟수를 다 쓰면 **멈추고 넘긴다.** 한 번 더 돌지 않는다 |
| `LOOP-04` | 횟수가 남아 있어도 **§4의 즉시 중단 조건**에 걸리면 그 자리에서 멈춘다 |
| `LOOP-05` | **통과 기준을 낮춰 초록 불을 만들지 않는다** (§6) |
| `LOOP-06` | 멈출 때는 **§5의 인계 코멘트**를 남긴다. "실패했습니다"만으로는 끝내지 않는다 |
| `LOOP-07` | **횟수는 이슈 코멘트에 적는다.** 상태를 갖는 것은 세션이 아니라 이슈다 (§5) |
| `LOOP-08` | **시작하거나 이어받을 때마다 §2 재진입을 거친다.** 세션이 바뀌어도 횟수는 이어진다 |
| `LOOP-09` | **CI 실행과 CI 실패 뒤 재확인은 1회로 세지 않는다** (§3) |
| `LOOP-10` | **CI 는 실패했는데 같은 커밋에서 로컬은 통과하면 사람에게 넘긴다** (§4) |

---

## 2. 재진입 — 시작하거나 이어받을 때

**루프는 세션보다 오래 산다.** 창을 닫았다 열거나 다른 사람이 이어받아도 같은 이슈의 같은 루프다. 그래서 **매번 여기서 시작한다.**

```
이슈를 연다
  ├─ 종료 조건(§3) · 최대 횟수(§6) 를 읽는다
  └─ 가장 최근 루프 상태 코멘트를 읽는다 → 없으면 attempt = 0
        ↓
  사람 차례로 넘어가 있나?   → 진행하지 않는다. 사람의 답을 기다린다
  attempt ≥ 최대?           → verify 를 돌리지 않고 그대로 넘긴다
  그 외                     → attempt 를 이어받아 루프 시작
```

- **횟수는 저절로 0이 되지 않는다.** 세션이 새로 시작해도 이어진다
- 0으로 돌리는 것은 **사람이 초기화 코멘트를 남길 때뿐**이다 (§5)
- 사람이 힌트를 주고 "다시 해보라"고만 하면 **횟수는 그대로 이어진다.** 초기화를 원하면 그렇게 적어야 한다

## 3. 무엇이 1회인가

이 정의가 없으면 "3회"가 아무 뜻도 없다.

| | |
|---|---|
| **1회로 센다** | 코드 수정 + `npm run verify` (로컬) |
| **세지 않는다** | 조사 · 원인 가설 · 계획 |
| | **CI 실행** — PR·푸시로 도는 것 (`LOOP-09`) |
| | **CI 실패 뒤 같은 커밋에서 돌리는 로컬 `verify`** — 재현 확인이지 새 시도가 아니다 |

- `verify` 를 돌리지 않은 수정은 1회가 아니다. **돌려야 결과를 안다**
- 한 번의 수정에서 파일 여러 개를 고쳐도 1회다
- `verify` 가 **같은 단계에서 같은 이유로** 두 번 연속 실패하면, 횟수가 남아도 진전이 없는 것으로 보고 §4에 따라 멈춘다

> 빠른 되먹임이 필요하면 루프 안에서 `npm run typecheck` · `npm test` 같은 부분 실행을 써도 된다. 다만 **1회로 세는 것은 `npm run verify` 전체**다. 부분만 통과한 상태로 횟수를 소진했다고 보고하면 안 된다.

## 4. 즉시 중단 조건 — 횟수와 무관

아래에 하나라도 걸리면 **남은 횟수를 쓰지 않고** 멈춘다.

| 조건 | 근거 |
|---|---|
| 작업이 [`ESCALATE-*`](./01-ssot.md#61-사람-판단-대기-escalate--구현-차단) 에 걸린 항목을 건드려야 한다 | SSOT §0.5 |
| 통과시키려면 **읽기 전용 영역**을 고쳐야 한다 | SSOT §0.6 |
| 이 일을 하려면 **`OOS-*`(Out of Scope) 에 있는 것** — 안 만들기로 한 것 — 을 만들어야 한다 | SSOT §2.3 |
| 지시가 요구사항 · 아키텍처 · 하네스 규칙과 충돌한다 | SSOT §0.5 |
| 이슈의 종료 조건이 서로 모순되거나 검증 불가능하다 | — |
| 같은 실패가 두 번 연속 동일하게 재현된다 (진전 없음) | §3 |
| **CI 는 실패했는데 같은 커밋에서 로컬 `verify` 는 통과한다** | `LOOP-10` |

**막혔다고 범위를 넓히지 않는다.** 이슈가 정한 경계 밖을 고쳐야 풀린다면 그것 자체가 넘길 내용이다.

> `LOOP-10` 이 따로 있는 이유 — 로컬과 CI 가 갈리면 원인이 코드가 아니라 **환경**이다 (OS · Node · 캐시 · 시각). 에이전트가 재현되지 않는 실패를 계속 파고드는 것을 막는다.

## 5. 상태 코멘트 — 어디에 무엇을 남기는가

**이슈 코멘트가 루프의 저장소다** (`LOOP-07`). 첫 줄이 `루프` 로 시작하는 코멘트가 상태이며, **가장 최근 것이 현재 상태**다.

### 5.1 회차 코멘트 — 매 회차 뒤

```
루프 2/3 · FAIL
단계: lint
바꾼 것: OutboundForm 의 렌더 중 Date.now() 를 daysSince() 로
달라진 것: typecheck 는 통과, lint 가 같은 규칙에서 계속 실패
다음: lib/date.ts 로 옮겨 순수 함수로 뺀다
```

### 5.2 인계 코멘트 — 멈출 때 (`LOOP-06`)

```
루프 3/3 · 사람 차례
사유: 최대 도달            (또는 ESCALATE · OOS · 읽기전용 · 진전없음 · CI불일치)
마지막 실패: lint — react-hooks/purity, TransferForm.tsx:100
가설: 렌더 중 Date.now() 호출. 헬퍼로 빼야 하는데 그 파일이 읽기 전용 영역이다
변경 파일: src/lib/expiry.ts · src/components/OutboundForm.tsx
근거: RULE-06 · REQ-N-06
종료 조건: C2 C3 C4 C5 통과 / C1 C6 수동 미확인
```

### 5.3 초기화 코멘트 — **사람만 남긴다**

```
루프 초기화 · attempt 0
사유: 접근을 바꾼다. 이전 3회는 폐기
```

에이전트는 이 코멘트를 **쓰지 않는다.** 재진입할 때 읽기만 한다 (§2).

### 5.4 완료 코멘트

```
루프 1/3 · 통과
종료 조건: C2 C3 C4 C5 통과 / C1 C6 수동 미확인
변경 파일: ...
```

수동 확인 항목은 **확인했는지 여부를 분명히 적는다.** 못 봤으면 못 봤다고 쓴다.

## 6. 루프 안에서 하지 않는 것

통과시키려고 아래를 하면, 초록 불이 거짓말이 된다.

- 기존 **테스트의 기대값**을 바꾸기 — 바꿔야 한다면 전제를 사람에게 검토받는다
- 테스트를 `skip` · `only` 로 우회하거나 지우기
- `npm run verify` 체인에서 단계를 빼기
- 린트 규칙을 끄거나 `eslint-disable` 을 붙이기
- 타입 오류를 `any` · `@ts-ignore` 로 덮기
- 검증 스크립트(`scripts/verify-*.ts`)나 CI 설정을 고치기 — **실행만 한다** (SSOT §0.6)
- 보호 경로 기준선을 승인 없이 `--update` 로 갱신하기
- **회차 코멘트를 건너뛰거나 나중에 몰아 쓰기** — 그러면 이어받을 수 없다

> 이 중 하나가 정말 필요하다고 판단되면 그것은 **정책 변경**이다. 루프를 멈추고 사람에게 넘긴다.

## 7. 로컬 · CI · 사람이 턴을 주고받는 구조

```
기계 구간 ─ 루프 (attempt 로 센다)
  코드 수정 → npm run verify (로컬)
      ↓ 통과
넘기기 ─ 커밋 · 푸시 · 회차 코멘트
      ↓
기계 구간 ─ CI (attempt 로 세지 않는다 · LOOP-09)
  ├─ 통과 → 사람 차례 (머지)
  └─ 실패 → 같은 커밋에서 로컬 verify 재확인 (세지 않는다)
        ├─ 같은 실패 재현 → 루프로 복귀, attempt 이어서 센다
        └─ 로컬은 통과   → 사람 차례 (LOOP-10)
      ↓
사람 구간 ─ 머지 · 판단 · 초기화
```

- [`02-verification.md`](./02-verification.md) — 무엇을 어떻게 검증하는가 (파이프라인 · 빈틈)
- [`04-workflow.md`](./04-workflow.md) — 어디서 일하고 끝나면 무엇을 넘기는가 (`WF-*`)
- `ESCALATE-*` 에 걸린 항목은 **통과/실패를 판정하지 않고 `차단` 으로 넘긴다**

> 한때 "구현 루프"와 "검증 루프"를 따로 뒀으나 **루프는 하나**다. 검증은 그 안에서 실행되는 방법이고, 절차는 루프가 아니라 작업 규칙이다.

## 8. 알려진 빈틈

- **코멘트를 쓰는 것도 에이전트다.** 이슈에 상태가 남으니 세션은 넘어서지만, **안 쓰면 아무것도 안 남는다.** 기계가 강제하지 않는다
- `npm run verify` 의 `test` 단계가 **실제 `dev.db`** 를 쓴다. 루프를 돌릴수록 시연 데이터가 오염될 위험이 있다
- `build` 단계가 ~90초라 루프 1회가 길다. 부분 실행으로 좁히는 관례는 §3의 주의만 있고 규칙은 없다
- 수동 확인 항목은 루프가 판정할 수 없다. 사람이 볼 때까지 **미확인**으로 남는다
- **`LOOP-10` 판정에 로컬 재확인이 필요**한데, CI 와 같은 커밋인지 확인하는 절차가 사람 손에 있다

---

## 9. 예정 · 미정

- 상태 코멘트를 **기계가 읽고 쓰는 방법** — 지금은 사람이 읽어도 되는 자유 형식이다. 파싱 가능한 형식으로 갈지
- `verify` 실패가 **환경 탓**(네트워크 · 캐시)일 때 횟수에 세는지 — `LOOP-10` 은 CI↔로컬 불일치만 다룬다
- 이슈가 없는 작업의 상태를 어디에 남길지 — 지금은 남길 곳이 없다
- 루프 횟수를 넘겼을 때 **사람이 개입하는 형식** — 코멘트인지 새 이슈인지
