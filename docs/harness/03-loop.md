# 03. 루프 — 언제 멈추는가

> 관련: [10-implementation-loop.md](./10-implementation-loop.md) · [02-verification.md](./02-verification.md) · `.github/ISSUE_TEMPLATE/maintenance.yml` §6

## 1. 핵심 규칙

| ID | 규칙 |
|---|---|
| `LOOP-01` | **1회 = 코드를 고치고 `npm run verify` 를 돌린 것.** 읽기 · 조사 · 계획은 세지 않는다 |
| `LOOP-02` | 기본 **최대 3회**. 이슈 §6 이 다른 수를 적었으면 그쪽이 우선한다 |
| `LOOP-03` | 횟수를 다 쓰면 **멈추고 보고한다.** 한 번 더 돌지 않는다 |
| `LOOP-04` | 횟수가 남아 있어도 **§3의 즉시 중단 조건**에 걸리면 그 자리에서 멈춘다 |
| `LOOP-05` | **통과 기준을 낮춰 초록 불을 만들지 않는다** (§5) |
| `LOOP-06` | 멈출 때는 **§4의 네 가지**를 남긴다. "실패했습니다"만으로는 끝내지 않는다 |

---

## 2. 무엇이 1회인가

이 정의가 없으면 "3회"가 아무 뜻도 없다.

```
조사 · 원인 가설          → 세지 않음
코드 수정                 ┐
npm run verify 실행       ┘ → 여기까지가 1회
```

- `verify` 를 돌리지 않은 수정은 1회가 아니다. **돌려야 결과를 안다.**
- 한 번의 수정에서 파일 여러 개를 고쳐도 1회다.
- `verify` 가 **같은 단계에서 같은 이유로** 두 번 연속 실패하면, 횟수가 남아도 진전이 없는 것으로 보고 §3에 따라 멈춘다.

> 빠른 되먹임이 필요하면 루프 안에서 `npm run typecheck` · `npm test` 같은 부분 실행을 써도 된다. 다만 **1회로 세는 것은 `npm run verify` 전체**다. 부분만 통과한 상태로 횟수를 소진했다고 보고하면 안 된다.

---

## 3. 즉시 중단 조건 — 횟수와 무관

아래에 하나라도 걸리면 **남은 횟수를 쓰지 않고** 멈춘다.

| 조건 | 근거 |
|---|---|
| 작업이 [`ESCALATE-*`](./01-ssot.md#61-사람-판단-대기-escalate--구현-차단) 에 걸린 항목을 건드려야 한다 | SSOT §0.5 |
| 통과시키려면 **읽기 전용 영역**을 고쳐야 한다 | SSOT §0.6 |
| 통과시키려면 **`OOS-*`(범위 제외)** 를 넘어야 한다 | SSOT §2.3 |
| 지시가 요구사항 · 아키텍처 · 하네스 규칙과 충돌한다 | SSOT §0.5 |
| 이슈의 종료 조건이 서로 모순되거나 검증 불가능하다 | — |
| 같은 실패가 두 번 연속 동일하게 재현된다 (진전 없음) | §2 |

**막혔다고 범위를 넓히지 않는다.** 이슈가 정한 경계 밖을 고쳐야 풀린다면 그것 자체가 보고할 내용이다.

---

## 4. 멈출 때 남기는 것

성공이든 실패든 아래 네 가지를 보고한다.

1. **몇 회 돌았는가** — `2/3` 처럼 소진과 한도를 함께
2. **회차마다 무엇을 바꿨고 무엇이 달라졌는가** — 실패 단계가 옮겨갔는지, 그대로인지
3. **마지막 실패 출력** — 어느 단계에서 어떤 메시지로 멈췄는지 원문 그대로
4. **막힌 지점의 가설** — 무엇 때문이라고 보는지, 그리고 그것이 `ESCALATE` 감인지

수동 확인 항목(브라우저로 봐야 하는 것)은 **확인했는지 여부를 분명히 적는다.** 못 봤으면 못 봤다고 쓴다.

---

## 5. 루프 안에서 하지 않는 것

통과시키려고 아래를 하면, 초록 불이 거짓말이 된다.

- 기존 **테스트의 기대값**을 바꾸기 — 바꿔야 한다면 전제를 사람에게 검토받는다
- 테스트를 `skip` · `only` 로 우회하거나 지우기
- `npm run verify` 체인에서 단계를 빼기
- 린트 규칙을 끄거나 `eslint-disable` 을 붙이기
- 타입 오류를 `any` · `@ts-ignore` 로 덮기
- 검증 스크립트(`scripts/verify-*.ts`)나 CI 설정을 고치기 — **실행만 한다** (SSOT §0.6)
- 보호 경로 기준선을 승인 없이 `--update` 로 갱신하기

> 이 중 하나가 정말 필요하다고 판단되면 그것은 **정책 변경**이다. 루프를 멈추고 사람에게 올린다.

---

## 6. 구현 루프와 검증 루프의 관계

둘은 번갈아 도는 별개의 루프가 아니다.

```
구현 루프 1회
  ├─ 코드 수정
  └─ npm run verify   ← 검증은 구현 루프 안에서 실행된다
        ↓ 실패
      다음 회차 (횟수 남았고 §3에 안 걸릴 때만)
        ↓ 통과
      검증 루프: 판정 기록 · 증거 · 수동 확인 항목 처리
```

- [`02-verification.md`](./02-verification.md) — 무엇을 어떻게 검증하는가 (파이프라인 · 빈틈)
- [`10-implementation-loop.md`](./10-implementation-loop.md) — 구현 루프의 절차 (⏳ 미정의)
- `ESCALATE-*` 에 걸린 항목은 **통과/실패를 판정하지 않고 `차단` 으로 보고**한다

---

## 7. 알려진 빈틈

- **횟수를 세는 주체가 없다.** 현재는 에이전트가 스스로 세고 스스로 보고한다. 기계가 강제하지 않는다
- `npm run verify` 의 `test` 단계가 **실제 `dev.db`** 를 쓴다. 루프를 돌릴수록 시연 데이터가 오염될 위험이 있다 (각 테스트가 자기 흔적만 지우는 것에 의존한다)
- `build` 단계가 ~90초라 루프 1회가 길다. 부분 실행으로 좁히는 관례는 §2 의 주의만 있고 규칙은 없다
- 수동 확인 항목은 루프가 판정할 수 없다. 사람이 볼 때까지 **미확인**으로 남는다

## 8. 예정 · 미정

- `10-implementation-loop.md` 를 **`04-` 로 옮길지** — 나머지는 `01`~`03` 으로 정렬됐는데 이것만 `10-` 이다. 내용이 채워질 때 함께 정하는 편이 낫다
- 루프 횟수를 **기계가 세는 방법** (커밋 수? verify 실행 로그?)
- 횟수 소진 후 재개 규칙 — 사람이 힌트를 준 뒤 다시 3회를 주는지, 이어서 세는지
- `verify` 실패가 **환경 탓**(네트워크 · 캐시)일 때 횟수에 세는지
